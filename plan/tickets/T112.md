## Do
- Nightly CronJob: `pg_dump` (custom format) plus object-storage mirror, restic-encrypted, to the off-cluster target in DECISIONS. Secrets only via Kubernetes Secrets (`RESTIC_REPOSITORY`, `RESTIC_PASSWORD`, S3 creds as env); nothing in git. Uses `DATABASE_URL` and the four `S3_*` names, converting the JDBC URL for `pg_dump` (FOLLOWUPS: env var contract).
- Weekly `backup-verify`: restore the latest snapshot into a scratch database (created C.UTF-8, FOLLOWUPS: V1 aborts on C ctype) and run row-count checks against counts recorded at dump time (`app.change` max seq, `app.review_log`, `app.note`, `app.card` counts, `ref.dict_entry` count) plus V1 migration checksum present.
- Failure goes to ntfy / alert (config key in values; if the ntfy workload is not yet deployed, the script posts to a configured URL and exits non-zero so a Job failure is also visible).
- Document in `deploy/backup/README` (the one docs file this ticket may add): the restore drill, and the known limit that after a restore REST- and job-originated ops since the last backup are lost while device ops are re-pushed (FOLLOWUPS: T005); state the backup frequency as a HUMAN_CHECKS item.
- Restore drill script `deploy/backup/restore-drill.sh` that runs against k3d.

## Acceptance
- [ ] The restore drill script is documented and passes in k3d: backup runs, `backup-verify` restores into a scratch DB and the row-count checks pass; failure injection (corrupt counts) makes it fail and notify.
- [ ] `make check MODULE=deploy` green (templates render with and without `backup.enabled`).
- [ ] No secret values appear in templates or the repo.
