## Do
Design the device-side seams in `kotobaya.sync.client`, in `commonMain`, explicit API mode, no platform types:
- `store/`: `DeviceStore` (one `transaction { }` entry; typed access to `pending_op`, `sync_state`, and the learning tables the apply code needs; designed to be implemented over the contract's `Local.sq`/`Learning.sq` by SQLDelight in T303c) plus an in-memory implementation used by tests. `SyncTransport` (push, pull, meta) with typed results/errors, and `Clock`/`Random` seams. `OpApplier` interface (implemented by T303b) that applies one op to local tables, called both for pulled ops and for the local effect of a minted op.
- `mint/`: `OpMinter`: mints the HLC (`mint`), builds the envelope, checks `max_op_bytes` from the durable `/meta` limits BEFORE minting (refuse with a typed error that the UI can show), and in ONE `DeviceStore` transaction applies the local effect through `OpApplier` and inserts the `pending_op` row (SYNC §4: crash never loses or half-applies). Minting is blocked while `rebuild_pending`.
- `protocol/`: `SyncEngine.cycle()` per SYNC §6.1 'Sync cycle': push all `pending` rows in ascending hlc in batches within `max_push_bytes`/op count; interpret per-op results (accepted/duplicate -> `acked` with `acked_seq`; rejected -> `rejected` with code and message, never purged); HTTP 413 alone -> `op_too_large`; transient errors keep rows `pending` and bump `attempts`; update `hlc_acked`, `remint_offset` (first clock code), `durable_seq`, `log_epoch` keys per §10.5; compare `log_epoch`/`high_water_seq` on every response and surface a `LogChanged` result for T303b to act on (apply nothing from that page); pull pages with per-page transaction, schema-validating each pulled op (stop-and-report 'update required' on unknown/invalid op at that seq, cursor stays before it), accept pages up to `max_push_bytes + max_op_bytes`, skip `device_applies=false` ops but advance the cursor, `observe` every pulled HLC; purge `acked` rows only when `acked_seq <= pull_seq` and `<= durable_seq`; set `last_sync_at`.
- `SyncStatus` data model for the UI (idle, syncing, offline, server unreachable, upgrade required with seq/op id/first error, clock wrong, pending/acked/rejected counts, last sync, last error), a pure function of store + last result.
- Backoff policy as a pure function (exponential with jitter, capped) used by T303c's WorkManager wrapper.

## Acceptance (each bullet -> at least one named test)
- [ ] SYNC §12.1-12.4 worked examples run as client-side tests against a test server (in-memory, built on the scenario/batch examples in `contracts/sync/examples`); every `contracts/sync/examples/raw-push` case's expected per-op outcome is reflected in the client's row states.
- [ ] Idempotency: pushing the same outbox twice (response lost) ends with each op `acked` once; a replayed pull page applies nothing twice.
- [ ] Crash safety: a store that throws between 'apply local effect' and 'insert pending_op' leaves neither; a transport that dies mid-push (before and after the server applied) leaves every op `pending` or `acked`, never missing; the retry converges (named 'kill-mid-push').
- [ ] Purge rule: an `acked` row survives until both `acked_seq <= pull_seq` and `<= durable_seq`; `durable_seq` of a new epoch is not mixed with the old.
- [ ] `max_op_bytes` below 1 MiB refuses to mint an oversize note op; unknown/invalid pulled op stops the pull and sets 'update required' without skipping; pull page larger than `max_push_bytes` is accepted.
- [ ] Client-side convergence fuzz: N>=3 simulated devices (in-memory stores, real `OpMinter`/`SyncEngine`, a stand-in `OpApplier` applying only the tiny op subset the fuzz generates) against the in-memory test server; random offline stretches and sync orders; after final syncs all replicas and the server agree per SYNC §11 (>= 100 seeds, deterministic by seed).
