## User request (2026-11-15)
"When I run out of reviews I should be able to continue reviewing (which just adds more cards until I stop). First-time cards should be marked with a tiny 'new' (Android too). When I run out it should say I'm done, as now, but with an option to keep reviewing. The Today page also gets a Keep going button (on Android the Review button changes to Keep going when out)."

## Today (scout)
- core QueueBuilder.kt:151-173: QueueLimits {newPerDay, reviewsPerDay, newPerSession, newShownThisSession, burySiblings, learnAheadMs}; rule 4 (~:259) caps new at min(newPerDay - introduced, newPerSession - shown); per-deck caps also apply. There is no override.
- GET /review/queue (openapi.yaml:2143): params limit, deck_id, kinds. QueueItem (:8872) has no new flag (Card.reps exists).
- Settings: scheduler.new_per_day / reviews_per_day / new_per_session (SCHEMA.md:560-562).

## Decision (provisional ADR; record it)
Keep going is a stateless per-request/session override, not a setting and not an op:
- core: an additive `keepGoing: Boolean = false` on QueueLimits (or QueueInput). When true, the builder ignores reviewsPerDay, newPerDay, newPerSession and per-deck new caps. Ordering, deck priority, sibling burying, suspended/buried/blacklisted/never_forget exclusions and learn-ahead are unchanged. Due reviews still come before new cards. It does NOT pull not-yet-due reviews (no study-ahead). When keepGoing yields nothing, the user is truly out of cards.
- API: GET /review/queue gains an optional `keep_going` boolean (default false) with the same semantics, plus whatever the response needs so clients can tell "done for today, more available with keep_going" from "nothing left at all". For example, an additive `more_available: boolean` (count of cards keep_going would add, capped) on the queue response when the normal queue is empty. Choose the cheapest correct shape and document it.
- QueueItem gains an additive `is_new: boolean` (card has never been reviewed: reps == 0 / state new) for the "New" badge. Core's queue item model carries the same thing so Android gets it offline.
- Limits accounting stays as is: cards introduced through keep going count as introduced today (they are), so they never raise tomorrow's allowance.
