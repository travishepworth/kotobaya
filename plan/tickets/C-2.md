## MAJOR (must fix)
A1. Duplicate JSON keys in a push (SYNC 5.2/5.3 ~268/315, batch.schema.json PushRequestLenient, core sync/Json.kt ~50/104, openapi ~3883). Rule: the server parses the body with a syntax-only, duplicate-tolerant parse. A duplicate key at the TOP level of the body, or a duplicated `op_id` within one push with different contents, fails PushRequestLenient → 400. A duplicate key anywhere inside `ops[i]` → per-op `rejected` / `schema_invalid`, decided BEFORE `op_too_large` (canonical size is undefined for such an element). Clients MUST push `CanonicalJson.encode` output (never contains duplicates). Mirror in core KDoc (Json.kt/OpCodec) and the API push description.
A2. SCHEMA 5.3 + Local.sq comment are stale: purge acked rows only when `acked_seq <= durable_seq` (SYNC 5.4); rejected rows follow SYNC 10.2 Retry / Discard (sets rebuild_pending + rebuild) / Re-mint (10.4); list the SYNC 10.5 sync_state keys. SCHEMA must say SYNC wins where they overlap.
B1. Backup/restore handshake: define `app.server_state` keys `log_epoch` and `durable_seq` (SCHEMA 4.4, V1 comment, SYNC 5.4/6.2). The backup job writes `durable_seq` = max(change.seq) contained in the dump, only after the dump is verified, monotonic. Name the restore hook (e.g. a server CLI subcommand such as `restore-finalize`, or a `restore_pending` server_state key checked at startup) that performs SYNC 6.2 steps (new epoch, raise HLC, set durable_seq) before serving. T112 (deploy/) and T202 (server) must both be able to implement it from the text alone.
B2. jpdb kanji import (openapi importJpdbHistory ~2524, JobResultJpdbHistory ~10698; read spikes/jpdb-map/REPORT.md "Export structure"). Real export has `cards_kanji_char_keyword` (2185 cards, 23k reviews) and `cards_kanji_keyword_char` (754 cards, 3k reviews). Specify: kanji rows → kanji notes (base type kanji; field/literal mapping) with card kinds char→keyword = `keyword`, keyword→char = `writing` (use the kind slugs the DB/core already define; if they differ, map to those); add kanji result buckets so "every input record is counted in exactly one bucket" holds. Grades: `unknown` → card creation only (no review), `known` → word.status_set known for vocab (no review), `pass` → rating 3 (button null), `fail` → rating 1 (button null), `hard` → rating 2 (button hard, ADR-008), others as already specified.
B3. Kanji render data (core render/CardRenderer.kt ~118, RenderInput/JsRenderInput; openapi QueueItem ~7894). Add `KanjiData(literal, meanings, onyomi, kunyomi, strokeCount?)` to RenderInput and JsRenderInput (JS-friendly types), and a `kanji` field to QueueItem, so auto_kanji notes with empty fields render from ref.kanji identically on every host.
