# C-24 — Search: bare terms match the dictionary forms of entry-linked vocab notes (BROWSE-1 root cause)

- Phase: P10 · Model: opus (architect) · Risk: high (search contract + SQL compiler, both dialects)
- Owned paths: core/src/commonMain/kotlin/kotobaya/contracts/search/**, contracts/db/SCHEMA.md (§4 "Notes:" search recipe), core search→SQL compiler and its tests (core/src/*/kotlin/kotobaya/search/**), docs/DECISIONS.md
- Module(s) for CI: core, contracts (+ server if its search tests change)

## Root cause (BROWSE-1 writer)
Vocab notes linked to a dictionary entry (from the dictionary, a jpdb import or deck-build) store `fields = {}` (the card renders from the dictionary), so `note.search_text` never contains 食べる, and the bare term never matches.

## Change (additive)
A bare `SearchTerm.Text` also matches when `n.entry_seq IS NOT NULL` and a live `ref.dict_entry_form` of that seq (kanji form or reading) has `form`/`norm` containing the pattern. For `norm`, the query is normalised with NFKC and katakana folded to hiragana. Postgres compiles an EXISTS subquery. The device (SQLite) does the same against its local ref tables. If the on-device dictionary package lacks a forms table, specify the fallback (e.g. the prefilter skips it and the residual matches against the dict lookup) and say so.
