## Do
Additive where possible. Phase 4 cannot ship without these definitions; downstream tickets (T401b, T404a, T404b, T411c, T407, T410) implement exactly what you freeze.
1. **Snapshot archive formats** (`contracts/db/SNAPSHOT.md`): (a) media content snapshot for `media.content_blob_hash` — segments, sentences (with `tokens`), occurrences, detected grammar spans (empty until Phase 5); (b) deck-item snapshot for `deck.content_blob_hash` (media and list decks). Format version, compression, header (`media_id`/`deck_id`, `content_version`), row encoding, ordering, size bounds, and the install rule (replace all rows of that media/deck in one transaction, set `installed_content_version`). Recommended: zstd JSON Lines (zstandard is already a worker dependency) so both Kotlin server/device and Python can read it; a SQLite file is acceptable if you justify it. One validation tool or JSON Schema per record kind under contracts/db so producers and consumers can be tested.
2. **Publish hand-off** (new server-internal kind, e.g. `media-publish`, worker enqueues, server claims; add to the SCHEMA.md "Jobs" table, C-9 rules): payload (`parent_job_id`, `media_id`, new vs existing media, title/kind/source/jpdb_id for `media.created`, deck options, content snapshot hash, deck snapshot hash, `JobResultMedia` numbers), dedupe key, idempotent retry, and the exact server transaction: `media.created` + `deck.created` (first import only, `caused_by_op_id`), install content rows, replace the media deck's `deck_item` rows, `media.content_published` (parsed, version n+1), `deck.content_published` — all in one transaction. Define `parse_status` transitions: who emits `media.content_published` with `parsing` at job start/reparse and `failed` on parent failure (same version, SYNC §7.6).
3. **Who writes media bulk tables.** Recommended: the worker writes NO `app.media*`/`occurrence`/`deck_item` rows; it uploads the snapshot blobs (inserting `app.blob` rows, `kind = snapshot`, `origin = build`) and the server installs rows from the snapshot inside item 2's transaction (one install path for server and devices; `media` FK ordering solved). Update SCHEMA.md §2 rule and §4.3 "Written by" accordingly, or document the alternative you choose. Restate the sentence-id stability rule (keep id when `(segment_id, ordinal, text)` unchanged) as a producer obligation.
4. **jpdb mapping corrections** (for T407): where unmapped jpdb vocabulary lives (e.g. a server-only table populated by the publish hand-off from `JobResultMedia.unmapped`, keyed by `jpdb_vid`, with the media ids it occurs in), how the user resolves one (map to a JMdict `seq`, or ignore), persistence across re-imports, and the effect (affected media decks are re-published from the importer's cache without refetching, e.g. by enqueueing `jpdb-deck-import` with a `remap_only` flag). Add the REST ops (list unresolved with occurrence totals; put/delete a correction). Decide and justify whether corrections are learning data (op-synced like `parse_override`, server-only, devices ignore) or import configuration (plain REST, server-only table). Prefer no new op type: a new op type forces every device to update (SYNC §6.1 unknown-op stop). Additive `V2__` migration if a table is needed; Flyway checksum of V1 must not change.
5. Close the two SUMMARY.md "Known gaps" entries; regenerate clients (`make check MODULE=contracts`).
