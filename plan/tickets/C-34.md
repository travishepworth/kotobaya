## Do
Redefine `until_stop` everywhere it is specified:
- `until_stop = until_stop_parts.learning + until_stop_parts.review + until_stop_parts.new`. `later` stays in `until_stop_parts` as information but is **not** summed.
- `LoopPresentation.untilStop` the same: `learning + review + new` of the projected parts. A pending answer that returns today moves into `later`, so it leaves the total (it is no longer doable now); `done` grows by one, so `done + untilStop` holds steady.
- C3: the review header shows `learning`, `review`, `new` (hide-if-0 rule unchanged); `later` is shown only in the later-today hint line, never as a header chip and never in Home's big number. The progress bar is `done / (done + until_stop)`; it may grow when a learning card comes due.
- Fix the ADR-049 example (9 ready + 14 on timers: `until_stop` 9, not 23) and every other worked example.
- New invariant P-I5 / loop invariant: `until_stop > 0` iff the state can serve a card now; terminal or `waiting` ⇒ `until_stop == 0`.
- Update parity expectations in contracts/api/shell/parity/*.json so their `until_stop` = learning + review + new.
- Mark ADR-038 C3 / ADR-049 C3 as amended by ADR-054 where the docs quote them.
