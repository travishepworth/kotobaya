## Diagnosis (live 0.1.9)
`core/.../contracts/queue/QueueBuilder.kt:248` (rule 2) and `DefaultQueueBuilder.kt:123-138` put every learning/relearning card due within now+20 min (`QueueLoader.kt:229`, learn-ahead) at the FRONT, ahead of already-due reviews. A relearning card graded Hard (due ~15 min) heads the queue again immediately → user sees the same card over and over while 301 reviews are due (live card 01a1d425…: ratings 1,2,2,2,2, relearning step 0). Pre-dates UI-WEB.

## Do
Change the ordering rule (contract text + implementation) to Anki-like behaviour: learning/relearning cards that are due NOW (due_at ≤ now) keep priority; cards due in the future within the learn-ahead window are only served when no due reviews and no new cards (within limits) remain. Record as a provisional ADR. Keep everything else in the queue contract unchanged. Check docs/SPEC.md review-queue section for any conflicting statement and note it in HANDOFF (do not edit SPEC).
Consumers: web (via core JS build) and Android both use core's QueueBuilder → fix applies to both; check whether the server builds queues too (server/ review queue endpoint) and whether it uses core's builder — if it re-implements, list it in HANDOFF as a needed follow-up (don't edit server).
