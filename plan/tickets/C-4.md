## Do (the mismatches found by the planner; confirm each, fix, and add any others you find)
1. **Vocab cards.** Contract says "a note and a card" for a vocab row. ADR-009(1): exactly one card, the `meaning` card (JP to EN), carrying the `cards_vocabulary_jp_en` history; no reading/production cards are generated. State the card kind. Decide and state what happens to `cards_vocabulary_en_jp` rows (the real export has none; the fixture also has none): they must still fall in exactly one bucket and must not create a production card (proposal: map the word and count it as `vocabulary_*`, events counted `reviews_skipped`; or ignore the array; pick one and keep the bucket sums true).
2. **Suspended writing cards.** `cards_kanji_keyword_char` (kind `writing`) cards are created **suspended** (`card.suspended`, preserved, never shown). Known-only kanji rows get a kanji note with a **suspended** card (ADR-009(3)). Document in the kanji section and in `kanji_carded` / `kanji_cards_created`.
3. **`known` handling.** Contract: every `known` event of a vocab row emits `word.status_set known`. ADR-009(3): only when `known` is the card's only event (about 65 vocab); `known` followed by reviews sets no override (FSRS schedules from the reviews); known-only vocab gets no card. Rewrite the Grades table row, `vocabulary_status_only`, `status_events_known`, `word_statuses_set` and the example numbers accordingly (keep the `reviews_total` identity true; say which bucket the ignored `known` of a reviewed row falls into).
4. **Repeated vid.** ADR-009(2): rows repeating a vid (about 260, different spellings) merge onto one note/card by `entry_seq`; events are interleaved by timestamp; exact duplicates (same timestamp and grade) are dropped; review ids are deterministic and unique (hash of vid, timestamp, grade, occurrence index). Add this to the description, add a bucket for dropped duplicate events (an additive required counter, e.g. `reviews_duplicate_dropped`, and extend the `reviews_total` sum), and say how it interacts with `vocabulary_total` (rows) vs distinct notes. If you prefer not to add a required field, say where else those events are counted.
5. **Kanji keyword.** ADR-009(4): if a kanji row carries keyword text, write it to the note's `keyword` field; otherwise leave it empty (filled from KANJIDIC by the renderer, user-editable). Today the contract says `fields = {"literal": character}` only. The real export has no keyword member (REPORT.md): name the optional tolerated member (for example `keyword` on a kanji row), or state that it is ignored if absent.
6. **Example and counts.** `JobJpdbHistory`: `cards_created` is about equal to notes created (the example shows 2x). Fix numbers so every sum holds.
7. Tolerance: rows with `from_anki: true` are accepted (FOLLOWUPS T207); unknown grades are counted, shapes may drift.
