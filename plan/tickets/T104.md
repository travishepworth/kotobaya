## Do
Ktor app with:
- Config from env with exactly these names: `DATABASE_URL` (JDBC form, as the Helm chart and compose already pass it), `S3_ENDPOINT`, `S3_BUCKET`, `S3_ACCESS_KEY`, `S3_SECRET_KEY` (plus `S3_REGION`, already set by the chart). No renamed variants (FOLLOWUPS: env var contract).
- Hikari + jOOQ, Flyway running `contracts/db/V1__init.sql` (reference it at build time; never fork it). Provide a `migrate` entry point (`java -jar ... migrate`, non-zero exit on failure) for T111's Helm hook (FOLLOWUPS: the Helm hook is a placeholder; T111 replaces it using your entry point). Normal startup runs migrations only when an env flag says so. Test and compose Postgres must be created with a C.UTF-8 ctype (e.g. `POSTGRES_INITDB_ARGS=--locale=C.UTF-8`), otherwise V1 aborts (FOLLOWUPS: V1 and LC_CTYPE=C).
- problem+json errors (`Problem` schema, `urn:kotobaya:problem:*` types), request ids, structured JSON logs (per-request `token.id`/`token.name` once T105a exists; this is the audit trail, v1 has no audit table).
- `/healthz` (liveness; the chart and compose probe exactly this), `/readyz` (Postgres reachable), `/metrics` (Prometheus), plus the OpenAPI `GET /api/v1/health` and `GET /api/v1/meta` (limits as constants; real sync head arrives with T202).
- Every other OpenAPI operation is registered as a 501 problem+json stub, derived from the spec so it cannot drift.
- `/readyz` takes a list of readiness checks so T202 can add "SYNC 10.5 startup replay finished" (FOLLOWUPS: C-1 -> T104/T111). Add only the extension point.
- On startup create `S3_BUCKET` if missing (FOLLOWUPS: compose SeaweedFS has no S3 auth config and the app must create the bucket).
- Auth hook points: a pluggable `Authenticator` and a scope-requirement lookup built from the spec's `security` entries, default allow, for T105a/b to fill (FOLLOWUPS: `x-auth: body-key` is a custom extension that T105b must implement by hand).
