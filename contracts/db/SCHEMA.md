## 1. Layout

- `ref.*` — reference data. Read-only for every client and for the API. Only the `dict-refresh`
  worker job writes it, replacing a release in one transaction.
- `app.*` — everything else, in three groups:
  - **learning data**: synced through ops, held on server and phone;
  - **media**: built by the server/worker; the small `media` row travels through ops, bulk rows
    travel as snapshots;
  - **system**: server bookkeeping, never synced.
- Flyway: run with the default schema `public` (history table in `public`). The migration creates
  `ref` and `app` itself and installs `pg_trgm` into `public`.
- **The database must not use `LC_CTYPE = C`/`POSIX`.** `pg_trgm` then indexes no Japanese text.
  The migration checks this and aborts. Use `C.UTF-8` or `en_US.UTF-8` (the `postgres:17` image
  default is fine; CloudNativePG's default `C` is not).

## 2. Global rules

1. **Ids.** UUIDs are generated by whoever creates the row (UUIDv7 unless stated), never by the
   database. Text form everywhere outside Postgres is canonical lowercase `8-4-4-4-12`.
   Reserved ids, identical on every replica:

   | Id | Row |
   |---|---|
   | `00000000-0000-7000-8000-000000000001` | `device`: the server itself (origin of server-emitted ops) |
   | `00000000-0000-7000-8000-000000000010` | `fsrs_params`: the Default preset |
   | `00000000-0000-7000-8000-000000000101` … `106` | `note_type`: built-in Vocab, Kanji, Phrase, Grammar, Sentence, Custom |

2. **Time.** Postgres `timestamptz`; device `INTEGER` epoch milliseconds UTC. The user's time zone
   appears only in `review_log.utc_offset_min` and the `scheduler.*` settings.
   `created_at` = wall time carried by the creating op. `updated_at` = wall-clock part of the
   highest HLC applied to the row. Both are therefore equal on every replica.
3. **Entry id.** "Entry" always means a JMdict sequence number (`ref.dict_entry.seq`, `bigint`),
   held in columns named `entry_seq` (or `seq` inside `ref`).
4. **Soft references.** `app.*` never has a foreign key into `ref.*`, and columns documented as
   "soft reference" have no foreign key at all. Readers must tolerate a missing target (entry not
   in the phone's dictionary subset, deleted media, sentence not installed).
5. **Tombstones.** Learning-data rows are never hard-deleted. `deleted_at IS NOT NULL` means
   deleted. Deletion is **permanent** (no undelete op) except `deck_item` and manual
   `sentence_grammar_span` rows, whose presence is a normal last-writer-wins value. Ops that
   arrive for a deleted row are still applied to its registers (so replicas converge) but never
   clear `deleted_at`; if the row is a merge loser they are additionally forwarded to the survivor
   (section 4.2). Queries for live data must filter `deleted_at IS NULL` — and for cards also the
   parent note's `deleted_at`.
6. **Language.** `language` columns hold a BCP 47 tag and are always `ja` in v1.
7. **JSON shapes** are given in the column comments. Unknown keys must be preserved on rewrite.
8. **Text offsets** into sentence text are UTF-16 code units, half-open `[start, end)`. Python
   code must convert from code points.
9. **Writes.** Learning-data tables are written only by the op-apply path (server) or the local
   apply function (device). Media bulk tables and `ref.*` are written only by worker jobs.

## 3. Clocks and last-writer-wins

`app.hlc` is a hybrid logical clock value stored as 54 characters:

```
0193a1b2c3d4-0001-01931f3e-0000-7000-8000-0000000000a1
└ 12 hex ms ┘ └ctr┘ └──────────── device uuid ─────────┘
```

Byte-wise string comparison is clock order and is total (the device id breaks ties). Postgres
uses `COLLATE "C"` on the domain; SQLite's default `BINARY` collation is equivalent. Never compare
HLCs with a locale-aware collation.

A **register** is one independently merged value. An op that sets register `r` to `v` at clock
`h` is applied as: *if `h` > stored clock of `r` (or none stored): write `v`, store `h`; else
ignore*. Equal clocks cannot occur for different ops; an equal clock means the same op, so
ignoring is idempotent.

**Creation.** A `*.created` op carries the row's initial values and its HLC `h`. It stamps
`clocks[r] = h` for every register whose initial value is **not the column default** (non-empty
string, non-empty set/array/object, non-NULL, or a boolean/number different from the default),
and for each key present with a non-empty value in a JSON-object column (`fields.<key>`,
`settings.<key>`, `templates.<kind>`). Registers left at their default get **no** clock. So a
creation value competes like any other write, while an untouched default never overwrites
anything (it loses to every op and is never forwarded in a merge). Applying a `*.created` whose
id already exists is a no-op.

Where clocks are stored:

- Tables with a `clocks` column: a JSON object `{register name: hlc}`. A register absent from
  `clocks` has never been written by an op (its value is the creation value) and loses to any op.
  Register names are listed in each table's `clocks` column comment. Dotted names such as
  `fields.sentence`, `templates.meaning`, `settings.order` address one key of a JSON object column.
  The `deleted` register stores the clock of the delete op.
- Tables with a single `hlc` (or `override_hlc`) column: the whole row (or the named value) is one
  register.

Example — two devices edit one note offline:

| Device | Op | Clock | Result |
|---|---|---|---|
| A | set `fields.meaning` = "to eat" | `…c3d4-0000-…a1` | applied |
| B | set `fields.meaning` = "eat" | `…c3d9-0000-…b2` | applied (newer) |
| B | set `tags` = `["anime"]` | `…c3d9-0001-…b2` | applied (different register) |
| A (arrives last) | set `fields.meaning` = "to eat (food)" | `…c3d5-0000-…a1` | ignored (older than `…c3d9`) |

Final row: `fields.meaning = "eat"`, `tags = {anime}`, on every replica regardless of arrival order.

### 4.2 Behaviour the schema encodes

**Note identity and merging ("same word added twice offline").** At most one live note may
reference a given `entry_seq`, `kanji_literal` or `grammar_point_id`. The server enforces this
with partial unique indexes; the device has ordinary indexes because it can legitimately hold two
such notes until it hears the server's verdict. The indexes are a safety net, never a reason to
reject an op: the server detects the collision first and merges.

*Trigger (server only).* While applying **any** op — `note.created`, or a `note.updated` that
wins the `entry_seq` register — the note N it targets would become a second live note for a
reference already held by live note W. Then N is the **loser** and W (the note already holding
the reference) the **survivor**, regardless of ids or clocks. The op itself is applied to N in
full first (values and clocks, exactly as on any replica; on the server the write that creates
the collision and the tombstoning of N must be one statement, or the unique index fires — see
`test/smoke.sql`); then, in the same transaction, the
server emits `note.merged {loser: N, survivor: W}` with `change.caused_by_op_id` = that op, and
applies it. `kanji_literal` and `grammar_point_id` are immutable, so they can only collide at
creation; `entry_seq` can collide at any time. Likewise a `card.created` colliding on live
`(note_id, kind)` yields `card.merged`.

*Applying `note.merged {loser L, survivor W}` — identical on every replica, server included:*

1. **Forward registers.** For every register `r` in `L.clocks` except `entry_seq` and `deleted`:
   apply `(L's value of r, L.clocks[r])` to W by the normal clock rule. Registers of L without a
   clock (defaults) are not forwarded.
2. Set `L.deleted_at` = wall time of the `note.merged` op (do **not** write `clocks.deleted`) and
   `L.merged_into_id = W`. Re-point any note whose `merged_into_id` is L to W.
3. **Cards.** For each card of L, live or not yet merged: find W's live card of the same `kind`.
   The server creates a missing one first (server-generated UUIDv7, emitted as an ordinary
   `card.created` op before the `card.merged`), then emits `card.merged {loser, survivor}` per
   card. Replicas do not pair cards themselves; they apply the `card.merged` ops they receive.
   A `card.created` for L arriving after the merge is applied to L, then merged the same way.

*Applying `card.merged {loser, survivor}`:* forward every register in the loser's `clocks` except
`deleted` to the survivor by the clock rule; set the loser's `deleted_at` and `merged_into_id`;
re-point cards merged into the loser; recompute the survivor's cache (its replay set grew).

*After the merge — on every replica.* Any op that writes registers of a row whose
`merged_into_id` is set (`note.updated` from a device that was still offline, `card.suspended`,
`card.flag_set`, `card.preset_set`, …) is applied **twice**: to the addressed row, and — except
for the `entry_seq` and `deleted` registers — to the survivor, each by the normal clock rule.
`note.deleted`/`card.deleted` addressed to a loser affect only the loser (deleting a duplicate
never deletes the survivor). Merges are permanent: changing a loser's `entry_seq` later does not
un-merge it.

*Why this converges.* The survivor's register `r` ends up holding the write with the highest
clock among all writes ever addressed to the survivor or to any of its losers. A replica that
saw a loser's write before the merge forwards it in step 1; a replica that sees it after the
merge forwards it by the rule above; the clock rule makes both orders, and repeats, give the same
result. No merged values travel in the op, so nothing depends on what the server happened to
hold when it merged.

Worked example. Phone A has note W for 食べる (`mnemonic = "tabby eats"` at clock 10). Phone B,
offline, creates note L for the same entry at clock 20 (`fields.sentence = "パンを食べる"`,
mnemonic left empty), then sets `tags = ["anime"]` at clock 30 and suspends L's meaning card at
clock 31.

| Step | Server / other replicas | Result on W |
|---|---|---|
| B pushes `note.created L` | collision → L applied, `note.merged L→W` emitted; step 1 forwards `fields.sentence`@20 | sentence filled; mnemonic kept (L's empty mnemonic has no clock) |
| B pushes `card.created` (L, meaning) | applied to L; `card.merged` → W's meaning card | — |
| B pushes `note.updated L tags`@30 | applied to L and forwarded | `tags = {anime}` |
| B pushes `card.suspended`@31 on L's card | applied to it and forwarded | W's meaning card suspended |
| B pulls `note.merged`, `card.merged` | B forwards L's clocked registers (sentence@20, tags@30) and the card's `suspended`@31 itself | same as everyone else |

`merged_into_id` never points at a row that itself has `merged_into_id` set (step 2 flattens).

**Deck natural keys.** `media` and `list` decks have a natural key (`media_id`, `list_key`) with
a server-side unique index, and no merge rule. They therefore must only ever be created by the
server (a media deck in the import job, with `deck.id = media_id`; a list deck when the user
enables a list through the API, under the op-apply lock, returning the existing live deck if
there is one). A client-originated `deck.created` with `type` `media` or `list` is rejected at
validation, before any table is touched. Clients need the server for these decks anyway: their
items only exist as server-built snapshots.

**Replay set.** The reviews that determine card C's schedule are all `review_log` rows whose
`card_id` is C *or any card with `merged_into_id = C`*, with `undone_at IS NULL` and
`review_type IN ('scheduled','learning','manual')`, ordered by `(reviewed_at, hlc, id)` — the
order of `contracts/sync/SYNC.md` 9.1, which is authoritative (C-1). `review_log.card_id`
is never rewritten. See the query in `test/smoke.sql`.

**Card cache.** `state … weights_version` on `card` are a pure function of (replay set, the
preset row, core version). Any replica may recompute them at any time and must do so when:
a review is applied whose `(reviewed_at, hlc, id)` sorts before the card's `last_review_id` row
(out-of-order arrival); a review in the replay set is undone; a card is merged into it;
`weights_version` differs from the preset's; `preset_id` changes; the core scheduler version
changed (SYNC.md 9.2, 10.5). A fresh card has `state = 'new'`, `due_at NULL`.

**`last_review_id` and `last_review_at` (C-1).** Walking the replay set in order:
- `last_review_id` = `id` of the last row folded, of any type (`scheduled`, `learning` or
  `manual`). It is the out-of-order marker: a new row sorting before it forces a full replay.
- `last_review_at` = `reviewed_at` of the last **rated** row (`scheduled` or `learning`). A
  `manual` row with `manual_action = 'set_due'` (reschedule) leaves it unchanged, so
  `last_review_id` may name a manual row whose `reviewed_at` differs from `last_review_at`. A
  `manual` row with `manual_action = 'reset'` sets it to NULL (the card is new again; the next
  rated row sets it afresh). NULL also when the replay set has no rated row.
- FSRS elapsed time for a rated row is its `reviewed_at` minus `last_review_at` (clamped ≥ 0;
  none when NULL). This is why a reschedule must not move it: a review shortly after a
  reschedule would otherwise use the same-day formula (e.g. S ≈ 26 d instead of ≈ 3.5 d after a
  lapse).
- The rule is a function of the ordered replay set, so folding one more row into the cache
  still equals a full replay (SYNC.md 9.3).

**Things deliberately not stored** (derived by the core on each replica): sibling burying (from
today's reviews of sibling cards), leech status (`lapses >= scheduler.leech_threshold`; the
search term `tag:leech` is virtual), hot-word and hot-kanji scores, coverage numbers, due counts.

**Review edge cases.**
- Duplicate `review.logged` (same id): no-op.
- Review for a card that is deleted or merged: still inserted; it is in the survivor's replay set
  if merged, and simply inert if deleted.
- Review for a card id the server has never seen: rejected (foreign key). Clients always push the
  creating ops first because push order is ascending HLC.
- Clock skew: replay order is by `reviewed_at` first, so elapsed time is never negative; implementations still clamp it to ≥ 0.
- Undo: `review.undone` at clock `h` is applied iff `undone_hlc IS NULL OR h < undone_hlc`
  (the **earliest** undo wins, whatever the arrival order); it then sets `undone_hlc = h` and
  `undone_at` = its wall time. Otherwise it is a no-op. An undo for a review id the replica does
  not have is a no-op on a device and rejected by the server (cannot happen in HLC push order).
- `review_log` and `change` are append-only by trigger on the server: any other `UPDATE`, and any
  `DELETE`, raises `restrict_violation`.
- `utc_offset_min` NULL = unknown; stats fall back to `scheduler.timezone`.
- Imported jpdb history: `import_source = 'jpdb'`, `device_id` = server device, `button` as
  mapped or NULL, `duration_ms` NULL, `hlc` built from the historical timestamp
  (`<historical ms>-<running counter>-<server device id>`).

**Word status.** `status = coalesce(override_status, auto_status, 'new')` (CHECK-enforced, so both
writers must set `status` in the same statement). `word.status_set` writes
`override_status`/`override_origin` at `override_hlc`; `word.status_cleared` writes
`override_status = NULL` at its clock (the row stays, so the clear beats older sets).
No row = `new`.

**Deck items.** Identity is `(deck_id, item_key)`, so concurrent adds of the same entry converge.
Adding a vocab note's word to a deck uses the entry form (`e:<seq>`) when the note has an
`entry_seq`, otherwise `n:<note id>`. For media and list decks, `hlc` is NULL and the rows come
from the snapshot in `deck.content_blob_hash`: on `deck.content_published {deck_id,
content_version, content_blob_hash}` a replica downloads the blob and replaces all items of that
deck in one transaction (device then sets `installed_content_version`). Until then it keeps the
old items.

**Confusables.** Pair is stored once per reason with `note_a_id < note_b_id`. If either note is
deleted the row stays and is hidden by readers; if either note is merged, readers resolve through
`merged_into_id`.

Deleting a media (`media.deleted`): server tombstones the `media` row, tombstones its deck
(emitting `deck.deleted`), then hard-deletes that media's segments, sentences, occurrences and
**detected** spans with explicit `DELETE`s (the `media` row itself is kept, so the
`ON DELETE CASCADE` clauses never fire in normal operation). Devices delete the same installed
rows. Manual spans, notes (`source_sentence` is held by value) and `review_log.sentence_id` are
untouched and may now dangle; `sentence_grammar_span.sentence_id` has no foreign key on either
side for exactly this reason.

**Manual spans.** Identity is `(sentence_id, grammar_point_id, start_offset, end_offset,
'manual')`. `grammar.span_put` and `grammar.span_removed` are whole-row last-writer-wins on `hlc`
(put → `deleted_at = NULL`, removed → `deleted_at` set), exactly like `deck_item`: two devices
highlighting the same span converge on one row, and a removed span can be added again.
`grammar.span_put` for an unknown or purged sentence is accepted and stored.

A jpdb-imported media has exactly one segment (`kind = 'whole'`, `ordinal = 0`), occurrences with
`sentence_ids = {}`, and no sentences.

**`change` invariants.**
- One row per accepted op, including ops that lose a last-writer-wins comparison (they are still
  part of the log) and server-emitted ops. A re-pushed `op_id` adds no row.
- An op and all its table effects commit in one transaction, together with its `change` row.
- `seq` order equals commit order (advisory lock `7033001`, see column comment). A pull
  `since = n` returns rows with `seq > n` ascending; because of the lock no row with a smaller
  `seq` can appear later.
- Never pruned in v1: a brand-new device replays from `seq = 0`.

Release rules: a refresh upserts by natural key inside one transaction and flips
`dict_release.is_current`. Entries that disappeared from JMdict keep their row with
`retired_release_id` set and lose their `dict_entry_form`/`dict_entry_gloss` rows (so they drop out

or prefix (`norm LIKE 'x%'`, btree); 3+ characters → `norm LIKE '%x%'` (trigram); English →
`gloss ILIKE '%x%'`; order by `dict_entry.freq_rank NULLS LAST`. Notes: `note.search_text`.
Sentences: `sentence.text`, `example_sentence.text`.

## 5. Device schema

Target: SQLite 3.18 (Android API 26 system SQLite), SQLDelight default dialect. `PRAGMA
foreign_keys = ON` is required on every connection.

### 5.1 Mapping

| Postgres | SQLite |
|---|---|
| `uuid` | `TEXT`, canonical lowercase |
| `timestamptz` | `INTEGER` epoch ms |
| `boolean` | `INTEGER` 0/1 (`AS kotlin.Boolean`) |
| `jsonb`, any array | `TEXT` containing JSON; arrays (`text[]`, `uuid[]`, `integer[]`, `double precision[]`) become JSON arrays |
| `app.hlc` | `TEXT` |
| `double precision` / `real` | `REAL` |

Example: Postgres `tags = '{anime,frieren}'` ⇔ SQLite `tags = '["anime","frieren"]'`.

`check.sh` fails if the two schemas drift apart in any way not listed in its allow-list.

### 5.3 Device-only tables (`Local.sq`)

Where this section and `contracts/sync/SYNC.md` overlap, **SYNC.md wins** (C-2).

- `pending_op` — outbox. The op row is written in the same SQLite transaction as its local effect.
  Push sends `state = 'pending'` rows in ascending `hlc` (SYNC.md 5.1).
  - `acked` rows may be purged only once **`acked_seq <= pull_seq` and `acked_seq <= durable_seq`**
    (`sync_state` values of the current `log_epoch`; SYNC.md 5.4). Until a verified backup covers
    an op, the device's row is the only copy that survives a server restore. A log reset (SYNC.md
    6.2) turns every `acked` row back into `pending` (`acked_seq = NULL`, `attempts = 0`).
  - A `rejected` row means the server permanently refused the op while its local effect is still
    applied. It MUST be shown to the user (sync status) with `last_error` (`"<code>: <message>"`),
    is never purged automatically, and leaves that state only through a user action of SYNC.md
    10.2: **Retry** (`state = 'pending'`, same `op_id` and `hlc`), **Discard** (delete the rows and
    set `sync_state.rebuild_pending = "1"` in one transaction, then the rebuild of SYNC.md 10.3),
    or **Re-mint** (clock rejections only, the default for them; SYNC.md 10.4). The one automatic
    transition is the bounded `unknown_reference` auto-retry after a log reset (SYNC.md 6.2).
- `sync_state` — text key/value. Keys listed in `Local.sq` (`device_id`, `pull_seq`, `hlc_last`,
  `last_sync_at`, `dict_release_id`) plus those of SYNC.md 10.5: `rebuild_pending`, `log_epoch`,
  `durable_seq`, `hlc_acked`, `remint_offset`, `core_scheduler_version` (C-1). SYNC.md 10.5 is
  authoritative for their meaning and their "absent means" value.
- `blob_cache` — which content-hashed blobs are wanted/cached.

### 5.4 The dictionary file

A separate SQLite file conforming to `Dict.sq`, `PRAGMA user_version = 1`, opened read-only.
It may hold a subset of entries; all child rows refer to entries present in the file.
The learning database must work with no dictionary file at all (all `entry_seq` lookups miss).

**`DICT_PACKAGE.md` (C-3) is authoritative** for the downloadable package (zstd, scope contents,
integrity rules), the diff format `kotobaya-dict-diff` v1, hashes and object keys, the shape of
`ref.dict_release.artifacts` (it adds `format_version` and `uncompressed_size_bytes` to the shape
in the column comment), and the device install/update algorithm. Its diff-apply connection is the
one exception to `foreign_keys = ON` above.

## 8. Verifying

```
contracts/db/check.sh
```

Starts a throwaway `postgres:17` container, applies `V1__init.sql`, runs `test/smoke.sql`,
confirms the migration refuses an `LC_CTYPE=C` database, loads the `.sq` files into `sqlite3`,
compares device and server columns and seed rows, and compiles the `.sq` files with the
SQLDelight Gradle plugin (`verify/`). The container is removed on exit.

Consumers wire SQLDelight exactly like `verify/build.gradle.kts` (two databases, `srcDirs`
pointing at `contracts/db/sqldelight/app` and `…/ref`), and may add their own query `.sq` files in
a second source directory; they must not redefine tables.
